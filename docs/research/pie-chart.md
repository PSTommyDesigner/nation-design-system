# Research Pie และ Donut Chart สำหรับ NTGDS

**วันที่วิจัย:** 2026-11-13
**โจทย์:** หาข้อมูลเพื่อออกแบบ component กราฟวงกลม (`PieChart` หรือ `DonutChart`) และชุดสีหมวด ใช้ครั้งแรกที่ One CMS Dashboard ส่วน "ข้อมูลเรียลไทม์วันนี้" ซึ่งมี 2 วงคู่กัน วงซ้ายเป็นสัดส่วนจำนวนข่าวที่เขียนตามหมวด วงขวาเป็นสัดส่วนยอดวิวตามหมวด ราว 6 ถึง 8 หมวด ใช้ดูว่าหมวดไหนเขียนเยอะแต่คนอ่านน้อย

**ป้ายแหล่ง:** `[ทางการ]` เอกสารหรือไฟล์ต้นทางขององค์กรเอง `[มาตรฐาน]` W3C `[แหล่งรอง]` ผู้เชี่ยวชาญหรือบริษัทภายนอก หรือข้อมูลที่ผู้วิจัยเปิดหน้าตรงไม่ได้ `[คำนวณ]` ผู้วิจัยคำนวณเอง `[ตีความ]` ความเห็นของผู้วิจัย ไม่ใช่ข้อเท็จจริง `[ของเรา]` ค่าที่อ่านจากไฟล์ในโปรเจกต์นี้

> **สิ่งที่ตัดสินแล้วใน [chart-component.md](chart-component.md) ไม่ค้นซ้ำ** ([1]) กราฟวงกลมอยู่ตระกูลเดียวกับ BarChart, เขียน SVG เองด้วย React กับ CSS Modules โดยใช้ `arc` จาก `d3-shape`, สีอ่อนต้องมีขอบเข้มตาม WCAG 1.4.11, การเข้าถึงคือชื่อสรุปของกราฟ ตารางข้อมูล ปุ่มดูเป็นตาราง และคำใบ้ใบเดียวที่ย้ายตามชิ้นที่ชี้หรือโฟกัส ส่วนคีย์บอร์ดใช้จุดหยุดเดียวแล้วเลื่อนด้วยลูกศรแบบเดียวกับ BarChart (`context/components/bar-chart.dsds.yaml`)
>
> **ข้อจำกัดของแหล่ง** หน้าเอกสารของ Spectrum (spectrum.adobe.com) ย้ายไปเว็บใหม่และเปิดด้วยเครื่องมือของผู้วิจัยไม่ได้ทั้งหน้าจริงและหน้าใน Web Archive ข้อมูล Spectrum จึงมาจากไฟล์อ้างอิงของ Spectrum 2 ในรีโป `adobe/react-spectrum-charts` ซึ่งเขียนว่าถอดค่ามาจากไฟล์ Figma "S2 Charts" ([7][8]) กับเอกสาร API ([9]) ส่วนประโยคจากหน้าเอกสารเก่า ([10][11]) มาจากข้อความสรุปของเครื่องมือค้นหา ติดป้าย `[แหล่งรอง]` ไว้ทุกจุด หน้า pie และ donut ของ Carbon ([3]) มีแค่ลิงก์ไปตัวอย่าง ไม่มีแนวทาง ค่าของ Carbon จึงอ่านจากไฟล์ต้นทาง ([4]) และ Salesforce Lightning หาแนวทางกราฟวงกลมของตัวเองไม่พบ จึงไม่ได้นับเป็นหนึ่งในเจ้าที่เทียบ

## 2. บริบทของเรา `[ของเรา]`

- token กราฟที่มีตอนนี้ (collection component) คือ `chart/color/series-1` (อ้าง `color/foreground/brand-primary` สว่าง brand-600 มืด brand-500), `series-2` (`utility/u-brand-200`), `series-2-border`, `grid`, `axis-text`, `hover`, `line` (`utility/u-orange-600`), `point-fill` ทั้งหมดอ้างถึง semantic ไม่ได้อ้าง primitive ตรง
- token กลุ่ม `color/utility/u-<hue>-<step>` ใน collection semantics มีครบ 16 hue (ams, bamboo, blue, brand, brown, cyan, fuchsia, gold, gray, green, orange, pink, purple, red, rose, yellow) ขั้น 50 ถึง 900 **ในโหมดมืดขั้นจะกลับด้าน** เช่น `u-orange-600` สว่างชี้ orange-600 มืดชี้ orange-400 (ขั้น s กลายเป็น 1000 ลบ s) ชุดสีที่อ้าง utility จึงได้โหมดมืดมาเอง
- พื้นหลังการ์ดโหมดสว่างคือ `background/primary/default` เป็นขาว โหมดมืดเป็น gray-dark-950
- ไม่มี token ความโปร่ง (opacity) ในระบบ ข้อนี้เกี่ยวกับข้อ 7

## 3. คำถามข้อ 1 pie หรือ donut และรูปทรง

### 3.1 แต่ละเจ้าเลือกอะไร

| เจ้า | pie หรือ donut | กลางวง | ความหนาวง | ระยะห่างระหว่างชิ้น | จุดเริ่มและทิศ | การเรียง |
|---|---|---|---|---|---|---|
| Carbon `[ทางการ]` | มีทั้งสอง | donut มีตัวเลขกับป้าย ค่าตั้งต้นของป้ายคือ "Total" | รูใน 3 ใน 4 ของรัศมี (วงหนา 25 เปอร์เซ็นต์ของรัศมี) | 0.007 เรเดียน | ค่าตั้งต้นของ d3 คือ 12 นาฬิกา ตามเข็ม | ตามลำดับข้อมูล (`sortFunction` เป็น null) |
| Spectrum 2 `[ทางการ]` | donut | ตัวเลขรวม (DonutSummary) กับป้ายใต้ตัวเลข | ค่าตายตัวตามขนาด 18, 20, 22px ที่เส้นผ่านศูนย์กลาง 120, 160, 200 | 2px (ขนาดเล็กสุด 1px ใหญ่สุด 4px) | 12 นาฬิกา ตามเข็ม | ชิ้นใหญ่สุดก่อน มากไปน้อย |
| Google Charts `[ทางการ]` | pie เป็นค่าตั้งต้น (`pieHole` 0) | ไม่มี | ปรับเองได้ | ขอบขาว | 12 นาฬิกา ตามเข็ม | ตามลำดับข้อมูล |

| Cloudscape `[ทางการ]` | มีทั้งสอง | donut แสดงผลรวม ถ้ากรองหมวดออกต้องแสดงผลรวมใหม่ | ไม่ระบุ | ไม่ระบุ | "12 o'clock position in clockwise direction" | มากไปน้อย หรือลำดับที่มีความหมายในตัว เช่น ระดับความรุนแรง |
| GOV.UK Analysis Function `[ทางการ]` | pie | ไม่กล่าวถึง | ไม่กล่าวถึง | ขอบขาวรอบทุกชิ้น | 12 นาฬิกา | เรียงตามขนาด |
| Maersk `[ทางการ]` | มีทั้งสอง | donut แสดงผลรวมได้ | ไม่ระบุ | ไม่ระบุ | 12 นาฬิกา | มากไปน้อย |

แหล่ง: Carbon [4], Spectrum [7][8][9], Google [12], Polaris [13][14][15], Cloudscape [16], Analysis Function [19], Maersk [20]

**สิ่งที่เห็นตรงกัน** เริ่ม 12 นาฬิกาเดินตามเข็มทุกเจ้าที่ระบุ, donut ใช้รูกลางแสดงผลรวม (Carbon, Spectrum, Polaris, Cloudscape, Maersk), ต้องมีตัวคั่นระหว่างชิ้นเป็นสีพื้น (Spectrum, Google, Analysis Function และ Atlassian ใน [5] ที่บอกว่าสีกราฟไม่ผ่าน 3 ต่อ 1 กันเองจึงต้องเว้นช่องหรือใส่ขอบ)

**สิ่งที่ต่างกัน** ความหนาวง แบ่งเป็นสัดส่วนของรัศมี (Carbon 25 เปอร์เซ็นต์, React Spectrum Charts `holeRatio` 0.85 คือวงหนา 15 เปอร์เซ็นต์ [9]) กับค่าพิกเซลตายตัวตามขนาด (Spectrum 2 [7], Polaris [13]) ไฟล์ของ Spectrum 2 เขียนชัดว่าไม่มี token สัดส่วนรู เพราะเส้นผ่านศูนย์กลางโตเร็วกว่าความหนาวงมาก มุมโค้งของชิ้น Spectrum 2 ห้ามโค้ง ([8]) ส่วน Polaris ใช้ 2px ([15])

### 3.2 ข้อเสนอ `[ตีความ]`

- **donut** เพราะการ์ดใน One CMS ต้องการตัวเลขรวม (ข่าววันนี้กี่ข่าว ยอดวิวรวมเท่าไร) และรูกลางคือที่ของมันพอดี ตัวเลขกลางวงใช้ text style ที่มีอยู่ ไม่ตั้งขนาดเอง
- **ความหนาวงเป็นค่าตายตัวต่อขนาดกราฟ** ตามแนว Spectrum 2 ซึ่งเข้ากับระบบเราที่ใช้ token ขนาดจาก spacing scale (`size/space/*`) มากกว่าสัดส่วน ตัวอย่าง ถ้าเส้นผ่านศูนย์กลาง 160 วงหนา 20 ถึง 24 (ใกล้ Spectrum 20 และ Carbon 20) ขนาดจริงต้องให้ผู้ใช้ตัดสินและเลือกจาก token ที่มี
- **ช่องคั่น 2px** วาดเป็นเส้นขอบของชิ้นสีเดียวกับพื้นการ์ด (`background/primary/default`) เพื่อให้โหมดมืดถูกเอง ค่า 2px ตรงกับ Spectrum 2 ขนาด S ถึง L ([7])
- **ไม่มีมุมโค้ง** ตาม Spectrum 2 เพราะช่องคั่น 2px บวกมุมโค้งจะกินชิ้นเล็กจนหาย (ข้อนี้ต่างจาก BarChart ที่มุมบนโค้ง 2px เป็นเรื่องที่ผู้ใช้อาจอยากให้เหมือนกัน ใส่ไว้ในคำถามข้อ 6)
- **12 นาฬิกา ตามเข็ม** ตรงกับค่าตั้งต้นของ `d3-shape` `pie()` ที่ startAngle เป็น 0 ไม่ต้องตั้งเพิ่ม
- **เรียงมากไปน้อยเมื่อเป็นวงเดี่ยว** ("อื่น ๆ" อยู่ท้ายเสมอ) ส่วนเมื่อสองวงเทียบกันดูข้อ 4.2

## 4. คำถามข้อ 2 จำนวนชิ้นสูงสุดและการรวมเป็น "อื่น ๆ"

| เจ้า | เพดาน | วิธีรวม |
|---|---|---|
| Atlassian `[ทางการ]` | สี 5 ถึง 6 สีต่อกราฟ "by grouping additional categories together" | รวมหมวดที่เกิน |
| Spectrum 2 `[ทางการ]` | 2 ถึง 6 ชิ้น (component ใน Figma มี variant Segment 2 ถึง 6) | มี token สีเฉพาะของถัง "Other" (`categorical-other`) |
| Spectrum หน้าเอกสารเก่า `[แหล่งรอง]` | แนะนำ 2 ถึง 3 ชิ้น ไม่เกิน 5 | ค่าที่ไม่แสดงรวมเป็น "other" |
| Cloudscape `[ทางการ]` | ไม่เกิน 5 ถ้าเกินให้ใช้แท่งซ้อน (stacked bar) | ไม่รวม ให้เปลี่ยนกราฟ |
| Maersk `[ทางการ]` | ราว 5 | รวมชิ้นเล็กเป็น "other" สีเทากลาง |
| GOV.UK Analysis Function `[ทางการ]` | 5 หรือน้อยกว่า | รวมหมวดได้ แต่ห้ามตัดหมวดออกจากผลรวม |
| Datawrapper `[แหล่งรอง]` | ราว 5 | รวมชิ้นเล็กเป็น "others" |
| Google Charts `[ทางการ]` | ไม่จำกัด | รวมชิ้นที่เล็กกว่าราวครึ่งองศาเป็น "Other" อัตโนมัติ |

แหล่ง: [5][7][8][10][16][20][19][21][12]

**ข้อเสนอ `[ตีความ]`**

1. แสดงหมวดที่มีชื่อได้ไม่เกิน 5 ชิ้น บวก "อื่น ๆ" 1 ชิ้น รวมไม่เกิน 6 ชิ้น ตรงกับเพดานของ Atlassian และ Spectrum 2 ที่สูงสุดในกลุ่ม
2. ถ้ามีพอดี 6 หมวด แสดงครบโดยไม่ต้องรวม (รวมหมวดเดียวเป็น "อื่น ๆ" ไม่ได้ข้อมูลเพิ่ม)
3. "อื่น ๆ" อยู่ท้ายสุดเสมอแม้จะใหญ่กว่าหมวดอื่น เพราะไม่ใช่หมวดจริง (Maersk และ Spectrum แยกสีให้มันเป็นพิเศษ) ใช้สีเทา `category-other`
4. คำใบ้ของชิ้น "อื่น ๆ" และตารางข้อมูลต้องบอกว่ารวมหมวดอะไรบ้าง ตามหลักของ Analysis Function ที่ห้ามข้อมูลหายจากผลรวม
5. ข้อมูลที่เป็นศูนย์ไม่วาดเป็นชิ้น แต่ยังอยู่ใน legend และตาราง (Cloudscape บอกว่าต้องมี legend เมื่อมีค่าศูนย์ [16])
6. **เคส One CMS ที่มี 7 ถึง 8 หมวดต้องตัดสินว่าใช้ 5 อันดับแรกตามอะไร** เพราะ 5 อันดับแรกของจำนวนข่าวอาจไม่ใช่ 5 อันดับแรกของยอดวิว ถ้าสองวงรวมหมวดต่างกัน ชิ้น "อื่น ๆ" ของสองวงจะหมายถึงคนละหมวด เทียบกันไม่ได้ ข้อเสนอคือใช้ชุดหมวดเดียวกันทั้งสองวง (ดูคำถามข้อ 2)

**ข้อเสนอ `[ตีความ]`**

- **legend ชุดเดียวใช้ร่วมสองวง** ไม่ใช่ legend แยกใต้แต่ละวง เพราะหมวดและสีเหมือนกันทั้งสองวง การมี legend เดียวบังคับให้สีตรงกันในตัว
- **วางใต้สองวง** (หรือระหว่างวงถ้าการ์ดกว้าง) เป็นแถวตาราง 3 คอลัมน์ จุดสีกับชื่อหมวด, % ข่าว, % ยอดวิว ตัวเลขดิบอยู่ในคำใบ้และตาราง ข้อนี้ทำให้ legend เป็นตัวเทียบไปในตัว แก้จุดอ่อนของ pie คู่ (ข้อ 4)
- **ไม่ใส่ป้ายบนชิ้นหรือป้ายนอกวง** ในรอบแรก เพราะชื่อหมวดภาษาไทยยาวกว่าภาษาอังกฤษ การ์ดในแดชบอร์ดแคบ ชิ้นเล็กจะไม่มีป้าย (React Spectrum Charts ตัดป้ายบนชิ้นที่เล็กกว่า 0.3 เรเดียน [9]) และ Spectrum ห้ามใช้ป้ายตรงคู่กับ legend
- จุดสีใน legend ใช้ขนาดเดียวกับ BarChart (`--ntg-size-space-s2-xs` 12) และไม่ต้องมีขอบ เพราะทุกสีผ่าน 3 ต่อ 1 แล้ว (ข้อ 6)

## 6. คำถามข้อ 4 สองวงเทียบกัน

### 6.1 สีหมวดเดียวกันต้องตรงกันทั้งสองวง

ทุกแหล่งที่พูดถึงตรงกัน Cloudscape เขียนว่าให้ข้อมูลชุดเดียวกันใช้สีเดียวกันในทุกกราฟ ([17]) Carbon และ Atlassian บังคับให้ใช้สีตามลำดับเลข ([2][5]) ซึ่งจะได้สีเดียวกันก็ต่อเมื่อหมวดได้ลำดับเดียวกัน **ดังนั้นสีต้องผูกกับหมวด ไม่ใช่ผูกกับตำแหน่งของชิ้นในแต่ละวง** `[ตีความ]` component ควรรับสีของแต่ละหมวดจากข้อมูล (เช่น `colorIndex` ต่อหมวด) ไม่ใช่ไล่สีตามลำดับที่ชิ้นถูกวาด

### 6.2 ลำดับชิ้นคงที่หรือเรียงตามค่าของแต่ละวง

ไม่มีเจ้าใดพูดถึงกรณีสองวงโดยตรง Cloudscape อนุญาตให้ใช้ "ลำดับที่มีความหมายในตัว" แทนการเรียงตามขนาดได้ ([16]) `[ตีความ]` **แนะนำลำดับเดียวกันทั้งสองวง** โดยเรียงตามวงซ้าย (จำนวนข่าวมากไปน้อย) แล้ววงขวาใช้ลำดับนั้นตาม เหตุผลคือ ถ้าเรียงแยกกัน หมวดเดียวกันจะไปอยู่คนละมุม คนอ่านต้องหาสีทีละชิ้น ส่วนถ้าลำดับเหมือนกัน วงขวาที่ "ไม่เรียง" จะเห็นได้ทันทีว่าหมวดไหนเสียตำแหน่ง ซึ่งคือคำถามที่แดชบอร์ดนี้ต้องการตอบพอดี ทางเลือกคือใช้ลำดับหมวดตายตัวของกองข่าว (เช่น ลำดับเมนูเว็บ) ซึ่งคงที่ทุกวันแม้ตัวเลขเปลี่ยน ต้องให้ผู้ใช้เลือก

### 6.3 ควรใช้ pie คู่หรือไม่ ความเห็นตรง ๆ `[ตีความ]` พร้อมแหล่ง

**pie คู่ไม่ใช่ตัวเลือกที่ดีที่สุดสำหรับคำถาม "หมวดไหนเขียนเยอะแต่อ่านน้อย"** ด้วยเหตุผล 4 ข้อ

1. คนตัดสินมุมและพื้นที่ได้แม่นน้อยกว่าความยาวบนแกนร่วม เป็นผลการทดลองที่อ้างกันแพร่หลายของ Cleveland และ McGill ([22], `[แหล่งรอง]` ผู้วิจัยไม่ได้เปิดเนื้อหาเต็มในรอบนี้) การเทียบชิ้นในวงหนึ่งกับชิ้นในอีกวงยากกว่าอีกขั้น เพราะไม่มีเส้นฐานร่วมเลย
2. GOV.UK Analysis Function แนะนำแท่งซ้อนเมื่อต้องเทียบสัดส่วนหลายชุด และแนะนำแท่งเมื่อหมวดมีขนาดใกล้กันหรือมีเกิน 5 หมวด ([19]) Datawrapper บอกว่า pie แสดงได้ผลรวมเดียว ถ้าจะเทียบสองชุดให้ใช้แท่งซ้อน ([21]) Cloudscape ให้เปลี่ยนเป็นแท่งซ้อนเมื่อเกิน 5 ชิ้น ([16]) เคสเรามี 6 ถึง 8 หมวดและเป็นการเทียบสองชุด จึงเข้าเงื่อนไขทั้งสองข้อ
3. ส่วนต่างที่ต้องการเห็น เช่น การเมือง 30 เปอร์เซ็นต์ของข่าวแต่ 12 เปอร์เซ็นต์ของยอดวิว ในวงกลมจะเห็นเป็นชิ้นใหญ่ในวงหนึ่งกับชิ้นกลางในอีกวงที่อยู่คนละมุม ส่วนในแท่งคู่ต่อหมวดจะเห็นเป็นแท่งสองแท่งยาวต่างกันวางชิดกัน
4. Spectrum 2 มี component "Small multiple donuts" ([7]) แสดงว่าการวางหลายวงเรียงกันเป็นรูปแบบที่ระบบใหญ่รองรับ แต่ใช้เพื่อดูภาพรวมของหลายกลุ่ม ไม่ใช่เพื่อเทียบค่าทีละหมวด

**ทางเลือกที่อ่านแม่นกว่า**

| ทางเลือก | ใช้ component | ข้อดี | ข้อเสีย |
|---|---|---|---|
| A แท่งแนวนอนคู่ต่อหมวด (% ข่าว กับ % ยอดวิว) เรียงตามส่วนต่าง | BarChart ที่มีอยู่ (ต้องมีแนวนอน) | ตอบคำถามตรงที่สุด ชื่อหมวดไทยอ่านได้เต็มบนแกน | BarChart ตอนนี้เป็นแนวตั้ง ต้องเพิ่มแนวนอน |
| B แท่ง 100 เปอร์เซ็นต์สองแถว (แถวข่าว แถวยอดวิว) | แท่งซ้อนซึ่งยังไม่มี | ยังสื่อ "ส่วนของทั้งหมด" เหมือน pie ตามที่ GOV.UK และ Datawrapper แนะนำ | ต้องสร้างแบบใหม่ |
| C donut คู่ + legend แบบตารางเทียบ | DonutChart ใหม่ | ตรงกับที่ทีมตัดสินไว้ใน One CMS (commit 20c12d6) เห็นภาพรวมเร็ว | การเทียบจริงเกิดใน legend ไม่ใช่ในวง |

**ข้อเสนอ** ถ้าทีม One CMS ยืนยันวงกลม ให้ทำทางเลือก C โดยมี 4 ข้อบังคับ คือ สีผูกกับหมวด, ลำดับเดียวกันทั้งสองวง, ชุดหมวดที่รวมเป็น "อื่น ๆ" เหมือนกันทั้งสองวง, และ legend เป็นตารางที่มีทั้ง % ข่าวและ % ยอดวิว และควรเก็บทางเลือก A ไว้เป็นรอบถัดไป

## 8. คำถามข้อ 6 ชุดสีหมวด 8 สีที่เสนอ `[คำนวณ]`

### 8.1 วิธีคำนวณ

สคริปต์อยู่ที่ scratchpad ของงานนี้ (`palette.mjs`, `palette2.mjs`, `search4.mjs`, `other.mjs`) อ่านค่าจาก `tokens/tokens.json/primitive.json` จริง แล้วทำดังนี้
1. คัดตัวเลือกทุก hue ขั้น 500 ถึง 700 ที่ผ่าน 3 ต่อ 1 บนพื้นขาว และขั้นคู่ในโหมดมืด (1000 ลบ ขั้น ตามการอ้างของ utility) ผ่าน 3 ต่อ 1 บน gray-dark-950 ตัดขั้น 800 ออกเพราะโหมดมืดจะได้ขั้น 200 ซึ่งอ่อนจนสีต่าง ๆ เข้าใกล้กัน (ทดลองแล้ว purple-200 กับ brand-100 ห่างกันแค่ 4.4)
2. แบ่ง hue เป็น 8 กลุ่ม (brand, ส้ม, ฟ้าอมเขียว, ม่วง, เขียว, ชมพูแดง, เหลือง, น้ำตาลหรือน้ำเงินอื่น) เลือกกลุ่มละ 1 สี ให้คู่ที่ใกล้กันที่สุดของทั้งชุดห่างกันมากที่สุด
3. วัดระยะสีด้วย CIEDE2000 ทั้งการมองเห็นปกติและจำลองตาบอดสี 3 แบบ (protan, deutan, tritan ความรุนแรงเต็ม ตามเมทริกซ์ของ Machado 2009 [27]) แล้วใช้ค่าต่ำสุดของ 4 แบบและของทั้งโหมดสว่างและมืด
4. เรียงลำดับให้ 6 สีแรกห่างกันทุกคู่มากที่สุด และทุกคู่ข้างกันแบบวนรอบ (ชิ้นที่ 8 ติดชิ้นที่ 1) ห่างกันมากที่สุด
5. บังคับสีที่ 1 เป็นสีเดียวกับ `series-1` ของ BarChart

### 8.3 ผลการตรวจ

**สีไหนต้องมีขอบเข้ม** ไม่มีเลยบนพื้นขาวและพื้น gray-light-50 (ต่ำสุดคือ category-2 ส้ม 3.34 บน gray-light-50) และไม่มีเลยบนพื้นมืด (ต่ำสุด category-1 4.71) ต่างจาก `series-2` ของ BarChart ที่ต้องมีขอบเพราะเป็นสีอ่อน **ถ้าวางกราฟบนพื้นอื่น เช่น การ์ดพื้นน้ำเงินอ่อน ต้องคำนวณใหม่** ส้ม (3.49) กับเขียว (3.73) เป็นสองสีที่จะตกก่อน

**ข้อจำกัดของการคำนวณ** การจำลองตาบอดสีเป็นแบบจำลองคณิตศาสตร์บน sRGB ไม่ใช่การทดสอบกับคนจริง Cloudscape เตือนว่าไม่ควรเชื่อแบบจำลองอย่างเดียว ([17]) ควรดูภาพจริงใน Figma ด้วยโหมดจำลองตาบอดสี และถามผู้ใช้จริงถ้าทำได้

### 8.4 ชื่อ token

เสนอ `chart/color/category-1` ถึง `-8` และ `chart/color/category-other` อยู่ใน collection component ข้าง `series-*` ที่มีอยู่ เหตุผลคือชื่อเป็นเลขลำดับตามแบบ Atlassian และ Spectrum ([5][7]) และคำว่า category ตรงกับความหมาย "หมวด" ของงานนี้ ส่วนช่องคั่นระหว่างชิ้นใช้ `color/background/primary/default` ได้ตรง ๆ หรือจะตั้ง `chart/color/slice-gap` เพื่อให้ Figma ผูกจาก collection component ได้ (ต้องถาม) ไม่เสนอ token สี hover แยกแบบ Atlassian ดูข้อ 9

สิ่งที่ต้องรู้ไว้คือ category-1 ซ้ำกับ series-1 และ category-2 ซ้ำกับ line ข้อดีคือแดชบอร์ดดูเป็นชุดเดียวกัน ข้อเสียคือถ้ากราฟวงกลมกับกราฟเส้นอยู่ใกล้กัน สีส้มจะหมายถึงสองเรื่อง

## 9. คำถามข้อ 7 การโต้ตอบ

| การโต้ตอบ | ใครทำ | รายละเอียด |
|---|---|---|
| ชี้แล้วเน้นชิ้น | Spectrum 2, Atlassian, Carbon, Cloudscape | Spectrum ชิ้นที่ชี้คงเดิม ชิ้นอื่นคงสีแต่ความทึบ 0.2 และ legend เน้นตาม ([7]) Atlassian ใช้ token `.hovered` หรือจางชิ้นอื่นด้วย `opacity.disabled` ([5]) Carbon ขยายรัศมีนอกของชิ้นที่ชี้ 3px ([4]) Cloudscape แสดง popover ตอนชี้ และตรึงไว้ตอนเลือก เพื่อให้ใช้ได้กับอุปกรณ์ที่ไม่มี hover ([16]) |
| คีย์บอร์ดเลื่อนระหว่างชิ้น | Cloudscape, Highcharts, BarChart ของเรา | Cloudscape ให้ใช้คีย์บอร์ดได้ทุกส่วน "in a logical and predictable order" ([16]) Highcharts รองรับการเลื่อนด้วยคีย์บอร์ดในโมดูล accessibility ([26]) ส่วน BarChart ของเราใช้จุดหยุดเดียวแล้วเลื่อนด้วยลูกศร Home End ตาม APG roving tabindex ([28]) |
| กดชิ้นหรือ legend เพื่อกรอง | Carbon, Cloudscape, Highcharts | Carbon legend กดได้เป็นค่าตั้งต้น ([4]) Cloudscape มีตัวกรองในตัวเมื่อมีอย่างน้อย 3 หมวด และบอกว่าเมื่อกรองต้องแสดงเปอร์เซ็นต์และผลรวมใหม่ ([16]) Highcharts วาดใหม่เหมือนชิ้นที่ซ่อนเป็นค่าว่างเป็นค่าตั้งต้น ([23]) |

**ความเสี่ยงของการกดเพื่อกรอง `[ตีความ]`**
1. เปอร์เซ็นต์ทุกชิ้นเปลี่ยนเพราะตัวหารเปลี่ยน คนที่ไม่ทันเห็นว่ากรองอยู่จะอ่านผิด เช่น การเมือง 30 เปอร์เซ็นต์กลายเป็น 40 เปอร์เซ็นต์
2. ในสองวงเทียบกัน ถ้ากรองแค่วงเดียว สองวงจะไม่เทียบกันได้อีก ต้องกรองพร้อมกันทั้งสองวง
3. ถ้ากดชิ้นแล้วกรองทั้งแดชบอร์ด (ไปหน้ารายการข่าวหมวดนั้น) เป็นกฎธุรกิจของ One CMS ที่ยังไม่มีในบรีฟ ต้องถาม
4. การกดชิ้นเล็กบนจอสัมผัสทำได้ยาก ต้องมีทางเดียวกันใน legend ด้วย

**ข้อเสนอรอบแรก `[ตีความ]`**
- ชี้หรือโฟกัสชิ้น แล้วชิ้นอื่นจางลง พร้อมเน้นหมวดเดียวกันในอีกวงและแถวเดียวกันใน legend คำใบ้ใบเดียวแสดงหมวด จำนวน และเปอร์เซ็นต์ของทั้งสองวง เพราะคำถามของผู้ใช้คือการเทียบสองค่านี้
- ระบบไม่มี token ความโปร่ง จึงต้องเลือกระหว่าง เพิ่ม token ความโปร่ง (เช่น 0.2 ตาม Spectrum) หรือใช้วิธีของ Spectrum แบบ "Emphasize" ที่เปลี่ยนชิ้นอื่นเป็นสีเทาทึบแทนการจาง ซึ่งใช้ `category-other` หรือ token เทาที่มีอยู่ได้ แต่จะสับสนกับชิ้น "อื่น ๆ" ต้องถาม
- คีย์บอร์ดใช้แบบเดียวกับ BarChart ลูกศรซ้ายขวาเลื่อนทีละชิ้นตามลำดับการวาด (ตามเข็ม) Home End ไปชิ้นแรกและชิ้นสุดท้าย Escape ปิดคำใบ้ ข้ามระหว่างวงด้วย Tab
- ยังไม่ทำกดเพื่อกรองในรอบแรก

## 10. คำถามที่ต้องให้ผู้ใช้ตัดสิน

1. **ยืนยันใช้ donut คู่ หรือเปลี่ยนเป็นแท่งแนวนอนคู่ต่อหมวด** (ทางเลือก A ในข้อ 6.3) สำหรับคำถาม "เขียนเยอะแต่อ่านน้อย" ถ้ายืนยันวงกลม จะใช้ทางเลือก C
2. **เมื่อมี 7 ถึง 8 หมวด เลือก 5 หมวดที่มีชื่อจากอะไร** จำนวนข่าว ยอดวิว หรือรายการหมวดตายตัว และยืนยันว่าสองวงต้องรวมหมวดเหมือนกัน
3. **ลำดับชิ้นในสองวง** เรียงตามวงซ้าย (จำนวนข่าวมากไปน้อย) หรือใช้ลำดับหมวดตายตัวของกองข่าว
4. **สีผูกกับหมวดแบบถาวร** (การเมืองเป็นสีเดียวกันทุกวัน ทุกกราฟ) หรือผูกกับอันดับของวันนั้น ถ้าถาวรต้องมีตารางจับคู่หมวดกับสีใน One CMS ซึ่งเป็นกฎของโปรเจกต์
5. **อนุมัติชื่อและค่า token สีหมวด** `chart/color/category-1` ถึง `-8` กับ `category-other` ตามตารางข้อ 8.2 และจะตั้ง `chart/color/slice-gap` หรือไม่
6. **ขนาดกราฟและความหนาวง** เส้นผ่านศูนย์กลางเท่าไร ความหนาวงใช้ token ขนาดตัวไหน และให้ชิ้นไม่มีมุมโค้ง (ต่างจากแท่งของ BarChart) ได้หรือไม่
7. **การเน้นตอนชี้** เพิ่ม token ความโปร่งสำหรับชิ้นที่ไม่ได้ชี้ หรือใช้การเปลี่ยนเป็นสีเทาทึบ
8. **กดชิ้นแล้วเกิดอะไร** ไม่ทำในรอบแรก, กรองทั้งสองวง, หรือพาไปหน้ารายการข่าวของหมวด (เป็นกฎธุรกิจของ One CMS)
