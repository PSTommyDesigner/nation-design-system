# Component Candidate

> ตั้ง 2026-11-26 เพราะข้อเสนอเคยกระจายอยู่ในกฎของแต่ละโปรเจกต์ โปรเจกต์อื่นมองไม่เห็นกัน
> กล่องตัวเลขจึงถูกสร้างซ้ำสองที่ คือ One CMS กับ AI Adoption Tracker โดยไม่มีใครรู้

## 1. candidate คืออะไร

ของที่โปรเจกต์ย่อยต้องใช้แต่ระบบยังไม่มี และเสนอเข้ามาเป็นทางการแล้ว เก็บที่ `candidates/<ชื่อ>/`
ยังไม่ใช่ component ของระบบ ห้ามใช้ในงานจริง และห้ามอยู่ใน `components/`

ดูทะเบียนทั้งหมดได้ที่หมวด Candidates ใน Storybook ซึ่งอ่านจากไฟล์ข้อเสนอโดยตรง

## 2. เช็คก่อนว่าใหม่จริงไหม

ของที่ดูเหมือนใหม่ ส่วนใหญ่เข้าหนึ่งในสามแบบนี้ ต้องตัดออกให้หมดก่อนจึงเสนอเป็น candidate

| สิ่งที่เจอ | ที่ที่ควรไป |
|---|---|
| เป็นแบบใหม่ของ component ที่มีอยู่ | เสนอเพิ่ม variant ของตัวเดิม ไม่ใช่สร้างตัวใหม่ |
| เป็น component เดิมหลายตัวประกอบกัน และหลายโปรเจกต์จะใช้ | `context/patterns/<ชื่อ>.dsds.yaml` |
| เป็น component เดิมหลายตัวประกอบกัน แต่ใช้โปรเจกต์เดียว | `context/features/<โปรเจกต์>/AGENTS.md` |
| ไม่มีอะไรใกล้เคียงเลย | เสนอเป็น candidate ตามหัวข้อ 3 |

## 3. โปรเจกต์ย่อยเสนอยังไง

1. คัดลอก `candidates/_template.candidate.yaml` ไปเป็น `candidates/<ชื่อ>/candidate.yaml` แล้วกรอกให้ครบ
   ชื่อโฟลเดอร์ต้องตรงกับช่อง `name` และเป็นตัวพิมพ์เล็กคั่นขีด
2. ช่อง `triedInstead` ต้องบอกว่าลอง component เดิมตัวไหนแล้วใช้ไม่ได้เพราะอะไร ไม่ใช่เขียนว่าไม่มี
3. ถ้ามีตัวอย่างให้ดู เขียนเป็น story ในโฟลเดอร์เดียวกัน ใช้ token `--ntg-` ล้วน ตั้งชื่อเรื่องขึ้นต้นด้วย `Candidates/`
   และใส่ `Banner` เตือนว่ายังไม่ใช่ component ของระบบ
4. รัน `npm run verify:candidates` ให้ผ่าน
5. เปิด Pull Request ที่แตะเฉพาะ `candidates/` ห้ามปนไฟล์อื่น แล้วแจ้งทีม Design System

## 4. ทีม Design System ตัดสินยังไง

ตัดสินใน Pull Request โดยแก้ช่อง `status` ของไฟล์นั้น

| status | ความหมาย | ทำอะไรต่อ |
|---|---|---|
| `proposed` | รอตัดสิน | ค่าเริ่มต้นตอนเสนอ |
| `accepted` | รับข้อเสนอแล้ว | เปิดงานสร้างจริง ไปหัวข้อ 5 |
| `building` | กำลังสร้างจริง | ตามรายการใน `components/AGENTS.md` |
| `merged` | รวมเข้า component เดิมเป็น variant | บอกใน `notes` ว่าเป็น variant ของตัวไหน |
| `rejected` | ไม่รับ | บอกใน `notes` ว่าให้ใช้อะไรแทน |

**รับ ไม่ได้แปลว่าย้ายโค้ดเข้า `components/` ทันที** เพราะ ntgds ออกแบบใน Figma ก่อน แล้วสร้างไฟล์ CSS จากค่าในไฟล์ Figma
โค้ดที่โปรเจกต์ย่อยส่งมาเป็นแค่ต้นแบบอ้างอิง

## 5. พอรับแล้วสร้างจริงยังไง

ตามลำดับเดิมของระบบ ไม่มีทางลัด

1. ค้นคว้าว่าระบบออกแบบใหญ่ ๆ ทำ component นี้แบบไหน ผลเก็บใน `docs/research/`
2. ออกแบบในไฟล์ Figma ผูกตัวแปรจาก collection `component` เท่านั้น และกำหนด effect ให้ด้วย
3. เขียนโค้ดตามรายการ New component checklist ใน `components/AGENTS.md`
4. ลงทะเบียนใน `context/design-system.dsds.yaml` และเขียน spec ใน `context/components/` เริ่มที่สถานะ `beta`
5. แจ้งโปรเจกต์ที่ขอให้เปลี่ยนมาใช้ตัวจริง แล้วลบของชั่วคราวออก

## 6. วันหมดอายุของของชั่วคราว

ทุกข้อเสนอต้องมี `expires` ห่างจาก `submitted` ไม่เกิน 30 วัน เพื่อไม่ให้ของชั่วคราวกลายเป็นของถาวรเงียบ ๆ

- ระหว่างรอ ของชั่วคราวอยู่ในไฟล์ story ของโปรเจกต์นั้นเท่านั้น ใช้ token ล้วน และติดป้าย `NEEDS CLARIFICATION`
- เลยกำหนดแล้วทะเบียนขึ้นป้ายแดง และรอบเตือนรายสัปดาห์เปิด issue ให้ทีมตัดสิน
- ถ้ายังตัดสินไม่ได้ ให้เลื่อน `expires` พร้อมเขียนเหตุผลใน `notes` ไม่ใช่ปล่อยค้าง

## 7. ด่านตรวจ

| คำสั่ง | ตรวจอะไร |
|---|---|
| `npm run verify:candidates` | ไฟล์ตรงแม่แบบ ช่องครบ ชื่อตรงโฟลเดอร์ สถานะอยู่ในชุด วันที่ถูกรูปแบบ ไม่เกิน 30 วัน และไม่มีขีดยาว |
| `npm run verify:candidates-expired` | เพิ่มการตรวจว่ามีตัวเลยกำหนดไหม ใช้ในรอบเตือนรายสัปดาห์ |

GitHub Actions `candidate-checks.yml` รันด่านนี้กับ Pull Request ที่แตะ `candidates/` ตรวจว่าไม่แตะไฟล์นอกโฟลเดอร์
และทุกเช้าวันจันทร์เปิดหรืออัปเดต issue ถ้ามีตัวเลยกำหนด

## 8. ที่เก็บของแต่ละอย่าง

| อะไร | ที่ไหน |
|---|---|
| ข้อเสนอ | `candidates/<ชื่อ>/candidate.yaml` |
| แม่แบบข้อเสนอ | `candidates/_template.candidate.yaml` |
| ตัวอย่างให้ดู | `candidates/<ชื่อ>/<Name>.stories.tsx` |
| กฎของโฟลเดอร์ฉบับภาษาอังกฤษสำหรับ AI | `candidates/AGENTS.md` |
| ทะเบียนที่คนอ่าน | หมวด Candidates ใน Storybook |
| ด่านตรวจ | `scripts/check-candidates.mjs` |
